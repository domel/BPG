TECHNICAL SPECIFICATION · BPG 1.0

Binary Property Graph (BPG)

A Parquet based property graph exchange format with GQL value metadata and an optional binary container.

StatusWorking draft
Updated28 October 2026
LanguageEnglish

Abstract

Binary Property Graph (BPG) represents a directed property graph in two Apache Parquet files. The node and edge schemas define identifiers, labels, and textual multi valued properties. Parquet file metadata carries a GQL type manifest and a graph schema document. An optional .bpg container packages the Parquet files with optional YAML metadata and a trailing CRC32. This specification defines the BPG 1.0 interoperability profile, including physical layouts, validation rules, reader and writer behavior, and implementation architecture.

Status of this document (informative)

This is a technical working draft, not a W3C Recommendation or an ISO standard. It draws from the supplied Graph Parquet Schema, GQL datatype and BPG container drafts, the research paper BPG: Efficient and Scalable Property Graph Serialization, and the implementations in bpg-graphfaker, bpg-pyarrow, bpg-container, and other BPG tools. Where the supplied texts agree, this document follows them. Where they disagree, it defines one BPG 1.0 profile consistent with the reference implementations.

Normative scope. Sections 3 through 10 define the interoperability profile. The introduction, tooling architecture, examples, and references are informative. A container reader may claim base container conformance without claiming graph profile conformance.

1. Introduction (informative)

A property graph has nodes, directed edges, labels, and named properties. Text exchange formats repeatedly encode structural delimiters and generally require full parsing before analytical scans. BPG uses Parquet's column projection, compression, and row groups while defining a fixed graph specific schema on top. The research paper evaluates this choice on real and synthetic graphs. Its measurements motivate the design; no throughput or compression figure is a conformance condition.

BPG has three separable concerns: the graph structure in Parquet, the semantic metadata in Parquet footers and Arrow fields, and the optional single file container. A directory containing nodes.parquet and edges.parquet is a complete dataset. The container is a transport representation of those payloads.

2. System context (informative)

The tooling suite described in the supplied DOCX has three primary modules. bpg-pyarrow provides Python and Arrow access to datasets and metadata. bpg-instance-validator uses that access layer to check structural, relational, and semantic rules. neo4j-bpg maps the same datasets into Neo4j. Additional tools produce datasets, inspect layouts, package containers, query snapshots, and compare graphs. The modules exchange BPG files rather than sharing a proprietary database format.

The architecture supports batch processing and streaming row group reads. The format itself does not prescribe a batch size, database transaction size, compression codec, or query engine.

3. Conformance

3.1. Requirement language

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are interpreted as described in RFC 2119 and RFC 8174 when written in capitals. A producer writes a BPG dataset or container; a reader decodes one; a validator evaluates conformance without necessarily exposing a graph API.

3.2. Conformance levels

Table 1. Conformance claims
LevelRequired behavior
Graph profile producerWrite the canonical Parquet schemas, identifiers, metadata, manifest, and graph schema document specified here.
Graph profile readerRead both Parquet files and interpret the graph structure and GQL metadata without silent loss of required information.
Base container readerValidate the header, sizes, section boundaries, version, and CRC32; payloads may remain opaque.
Graph container readerMeet base container requirements and validate the embedded files against the graph profile.

A schema check alone does not establish instance validity: primary keys and foreign keys require examination of data values. The optional YAML section does not replace the per file GQL manifest.

4. Graph data model

4.1. Identity and topology

A node is a row in nodes.parquet with an INT64 identifier. An edge is a row in edges.parquet with its own INT64 identifier and two INT64 endpoint identifiers. Node IDs MUST be non-null and unique within the node table. Edge IDs MUST be non-null and unique within the edge table. Both endpoints MUST reference existing node IDs. Node and edge identifier spaces are independent. Self loops and parallel edges are permitted.

4.2. Labels and properties

label is a nullable list of non-null UTF-8 strings. properties is a nullable list of non-null records. Each record has a non-null string key and a non-null list values whose string elements are non-null. Zero length lists are valid. The format does not impose uniqueness on labels or property keys. Consumers that interpret properties as a map SHOULD define a duplicate key policy at the application layer.

Null and an empty list are distinct physical values. A lossless reader MUST NOT merge them. Ordering of labels, property records, and property values is preserved by the Parquet list representation, although the graph model does not assign additional semantics to that order.

4.3. Value scope

The canonical graph columns store property values as strings. The GQL datatype metadata layer can describe a wider set of value types in an extended Parquet layout. An extension using typed columns MUST identify those columns through its manifest; it is outside the strict three column node and five column edge schema. Reference values such as node, edge, and graph objects are outside the GQL value mapping in this specification.

Canonical producers MUST use these columns in this order and MUST NOT add columns to the strict graph profile. Extension readers MAY accept extra columns if required columns retain their meaning. Parquet does not enforce the key constraints in Tables 2 and 3; a graph validator must examine values.

5.3. Dremel style physical schema

Lists MUST use the standard three level Parquet LIST annotation. Strings use STRING, historically called UTF8. The following notation states repetition and nested nullability explicitly. Field names used by Arrow for the intermediate list level may vary; logical structure and nullability govern compatibility.

message nodes {
  required int64 id;
  optional group label (LIST) {
    repeated group list {
      required binary element (STRING);
    }
  }
  optional group properties (LIST) {
    repeated group list {
      required group element {
        required binary key (STRING);
        required group values (LIST) {
          repeated group list {
            required binary element (STRING);
          }
        }
      }
    }
  }
}

message edges {
  required int64 id;
  required int64 source_node_id;
  required int64 target_node_id;
  // label and properties have exactly the same types as in nodes.
}

In the source draft, values is shown in a compact legacy list notation. The three level form above follows its stated logical type and the Arrow schemas used by the implementations. A reader SHOULD normalize equivalent Parquet list encodings through the Parquet library before applying logical checks.

5.4. Arrow equivalent

label = pa.list_(pa.field("element", pa.string(), nullable=False))
properties = pa.list_(pa.field(
    "element",
    pa.struct([
        pa.field("key", pa.string(), nullable=False),
        pa.field("values", pa.list_(
            pa.field("element", pa.string(), nullable=False)
        ), nullable=False),
    ]),
    nullable=False,
))
nodes = pa.schema([
    pa.field("id", pa.int64(), nullable=False),
    pa.field("label", label, nullable=True),
    pa.field("properties", properties, nullable=True),
])
edges = pa.schema([
    pa.field("id", pa.int64(), nullable=False),
    pa.field("source_node_id", pa.int64(), nullable=False),
    pa.field("target_node_id", pa.int64(), nullable=False),
    pa.field("label", label, nullable=True),
    pa.field("properties", properties, nullable=True),
])

This excerpt omits field metadata for readability. Section 6 defines the metadata that a canonical producer adds to every field.

6. File and graph metadata

6.1. Parquet footer keys

Each canonical graph Parquet file MUST contain the following UTF-8 key and value pairs in its file metadata. The graph schema document describes both tables even when embedded in one file. The gql manifest is per file and therefore lists that file's columns.

6.2. GraphParquetSchema document

The document MUST identify schemaFormat as GraphParquetSchema and formatVersion as 1.0. Its tables object declares the node and edge fields, field nullability, primary keys, and the edge foreign keys. The nested type description MUST agree with the actual Parquet schema. The fileMetadata object may restate the file name and version; notes may record cardinalities. These descriptive fields do not override the physical schema.

{
  "schemaFormat": "GraphParquetSchema",
  "formatVersion": "1.0",
  "tables": {

      "fields": [

        {"name":"label","type":{"name":"list","element":{"name":"string","nullable":false},"nullable_elements":false},"nullable":true},
        {"name":"properties","type":{"name":"list","element":{"name":"struct","fields":[
          {"name":"key","type":{"name":"string"},"nullable":false},
          {"name":"values","type":{"name":"list","element":{"name":"string","nullable":false},"nullable_elements":false},"nullable":false}
        ]},"nullable_elements":false},"nullable":true}
      ],
      "constraints": {"primaryKey":["id"]}
    },
    "edges": {
      "fields": [
        {"name":"id","type":{"name":"int64"},"nullable":false},
        {"name":"source_node_id","type":{"name":"int64"},"nullable":false},
        {"name":"target_node_id","type":{"name":"int64"},"nullable":false},
        {"name":"label","type":{"name":"list","element":{"name":"string","nullable":false},"nullable_elements":false},"nullable":true},
        {"name":"properties","type":{"name":"list","element":{"name":"struct","fields":[
          {"name":"key","type":{"name":"string"},"nullable":false},

          {"fields":["target_node_id"],"refTable":"nodes","refFields":["id"]}

      }

  },
  "fileMetadata":{"name":"BPG","version":"1.0"},
  "notes":{"labelsCardinality":"0..*","propertyValuesCardinality":"0..* per key","nonNullElements":"labels and values elements are non-null"}
}

A validator MUST compare declared field names, types, nullability, and constraints with the canonical profile. It MUST NOT assume that JSON declarations have been enforced by Parquet itself.

6.3. Schema extension

A future format version may add new metadata or columns. A BPG 1.0 strict reader MAY reject unknown required columns or an unsupported major version. An extension reader MAY ignore unknown optional JSON members while preserving the canonical graph fields. Producers MUST NOT reuse an existing field name for a different meaning under the same version.

7. GQL value metadata

7.1. Manifest

Each Parquet footer MUST contain one UTF-8 JSON value under gql. The root object MUST have version, matching MAJOR.MINOR.PATCH, and a columns object. The BPG 1.0 manifest version is 1.0.1. Every physical column MUST have an entry with string members originalType and physical. The optional root members dialect and defaults specify a GQL dialect, default temporal unit, and time zone policy.

Table 5. Manifest members
MemberType and rule
versionRequired semantic version string.
dialectOptional string, for example ISO/IEC 39075.
defaults.temporalUnitMILLIS, MICROS, or NANOS.
defaults.timezonePolicyUTC_ONLY, REQUIRE_TZ_COLUMN, or ALLOW_LOCAL.
columns.*.originalTypeRequired GQL type expression.
columns.*.physicalRequired Parquet carrier description.
columns.*.encodingBit encoding for a custom binary carrier.
columns.*.nullableOptional boolean; must agree with the actual field.
columns.*.precision, scale, maxLengthNumeric type parameters.
columns.*.temporalUnit, timezoneTime unit and IANA zone identifier.
columns.*.compatColumnName of an optional compatibility column.
columns.*.listelementNullable boolean and positive depth.
columns.*.recordopen boolean and optional fields array.

7.2. Field metadata

Arrow field metadata uses keys prefixed by gql:. Canonical producers MUST write gql:type for every required column. The values are int64 for identifiers, list<string> for labels, and list<record{key:string,values:list<string>}> for properties. Other keys include gql:codec, gql:precision, gql:scale, gql:maxLength, gql:nullable, gql:temporalUnit, gql:timezone, gql:compatColumn, gql:list.elementNullable, gql:list.depth, gql:record.open, and gql:record.fields. A reader SHOULD prefer a field annotation over a conflicting manifest parameter and report the conflict.

The following mapping covers extension value columns. The canonical graph layout continues to use the fixed columns in Section 5. A producer MUST supply enough metadata to reconstruct a value without loss when Parquet's logical type is insufficient.

A binary RAW column MUST declare its bit encoding. A reader MUST NOT guess byte order or signedness. For a zoned temporal value, gql:timezone or a string timezone column MUST identify the IANA zone. Parquet's adjusted flag does not retain that name. A producer MAY add a SQL friendly COMPAT column referenced by compatColumn; a lossless reader SHOULD use RAW. Such columns extend the strict graph schema.

7.4. Node manifest example

{
  "version": "1.0.1",
  "columns": {
    "id": {"originalType":"int64","physical":"INT64","nullable":false},
    "label": {"originalType":"list<string>",
              "physical":"LIST<BYTE_ARRAY(STRING)>","nullable":true,
              "list":{"elementNullable":false,"depth":1}},
    "properties": {
      "originalType":"list<record{key:string,values:list<string>}>",
      "physical":"LIST<STRUCT{key:BYTE_ARRAY(STRING),values:LIST<BYTE_ARRAY(STRING)>}>",
      "nullable":true,"list":{"elementNullable":false,"depth":1}
    }
  }
}

The edge manifest adds non-null source_node_id and target_node_id entries with type int64.

8. Binary container

8.1. Organization

A BPG 1.0 container contains a fixed 256 byte header, optional UTF-8 YAML metadata, two complete Parquet payloads, and a trailing four byte CRC32. Its size MUST be 256 + metadata_size + nodes_size + edges_size + 4. Node and edge payload sizes MUST be positive. All integers are unsigned little-endian.

8.2. Header byte layout

Table 7. BPG container header
OffsetBytesTypeField
08byte[8]magic
82uint16version_major
102uint16version_minor
124uint32header_size
168uint64metadata_size
248uint64nodes_size
328uint64edges_size
408uint64metadata_offset
488uint64nodes_offset
568uint64edges_offset
6448char[48]metadata_name
1128char[8]metadata_ext
12048char[48]nodes_name
1688char[8]nodes_ext
17648char[48]edges_name
2248char[8]edges_ext
23224byte[24]reserved

magic MUST equal 42 50 47 00 00 00 00 00. The version fields MUST be 1 and 0; header_size MUST be 256. Producers MUST zero reserved bytes. Readers MUST reject unsupported versions before interpreting offsets.

8.3. Offsets and names

metadata_offset = 256 if metadata_size > 0 else 0
nodes_offset    = 256 + metadata_size
edges_offset    = nodes_offset + nodes_size
file_size       = edges_offset + edges_size + 4

Producers MUST write these explicit offsets. Readers MUST check arithmetic without overflow, require contiguous sections, and require the payload to end exactly before CRC32. Name fields contain UTF-8 with zero padding. Base names omit paths and extensions; extension fields omit the dot. Canonical names are metadata.yaml, nodes.parquet, and edges.parquet. Producers MUST NOT store path separators. Readers MUST constrain extracted paths to the selected destination.

8.4. Integrity field

The final four bytes hold standard CRC32, little-endian, over every previous byte. The algorithm matches binascii.crc32(data, 0) & 0xffffffff. Readers MUST compare it before declaring a container valid. CRC32 detects accidental changes but does not authenticate a publisher.

9. Processing and validation

9.1. Writer algorithm

  1. Assign unique signed 64 bit node and edge IDs, then check edge endpoints.
  2. Build canonical Arrow schemas, including nested nullability and gql:type. Write complete Parquet files.
  3. Add the six footer keys from Table 4, a per file GQL manifest, and the graph schema document.
  4. If packaging, encode optional YAML as UTF-8, compute section lengths, and write the 256 byte header with canonical offsets.
  5. Write payloads in order and append CRC32 computed over the prefix.

9.2. Reader algorithm

  1. Reject a container shorter than 260 bytes. Parse the header before using declared lengths for allocation.
  2. Validate magic, version, header size, positive Parquet lengths, canonical offsets, exact total size, and section bounds.
  3. Compute CRC32 incrementally and compare it with the final field.
  4. Open both payloads as complete Parquet files; validate required schemas and metadata if claiming graph conformance.
  5. Scan identifiers for duplicates and nulls, then verify that edge endpoints reference nodes.

9.3. Validation outcomes

Table 8. Validation classes
ConditionOutcome
Bad magic, version, length, offset, overlap, or CRC32Container error
Unreadable Parquet, wrong field type, order, or nullabilityStructural error
Missing or malformed manifest or graph schema JSONMetadata error
Duplicate ID or missing edge endpointInstance error
Manifest and field metadata conflictSemantic diagnostic; strict validation may reject

A validator SHOULD report file, field, rule, and a bounded sample of failing rows. Metadata inspection alone cannot prove primary or foreign key validity. Reader resource limits should be applied before scanning.

9.4. Version handling

This specification defines one BPG container version: 1.0. Parquet file metadata uses version = 1.0, GraphParquetSchema uses formatVersion = 1.0, and the GQL manifest uses version = 1.0.1. These fields version different layers. Readers MUST NOT treat them as alternative container versions. An unsupported major container version MUST be rejected.

10. Security and robustness

Readers MUST check size arithmetic and section bounds before allocation or extraction. Implementations SHOULD limit payload size, row count, nested list depth, JSON depth, and decoded string length. YAML should be parsed with a safe data loader; metadata must not execute code. File names from container headers are untrusted. Absolute paths, separators, traversal sequences, and names resolving outside the destination MUST be rejected or replaced.

CRC32 is not a cryptographic signature. Applications requiring authenticity should use an external signature or authenticated delivery channel. A COMPAT column may be a lossy projection and should not silently replace RAW data.

11. Tooling architecture (informative)

11.1. Python access layer

bpg-pyarrow is Module A in the supplied Tooling Suite design. It provides dataset access, schema construction, metadata parsing, inspection, and Arrow batch reads. The design identifies conceptual responsibilities named BPGGraph, BPGDatasetReader, BPGDatasetWriter, GQLManifestParser, and MetadataInspector. These names describe responsibilities; they are not a guarantee that every release exports identically named classes. Inspection commands include bpg-info and bpg-dump-metadata.

11.2. Instance validator

bpg-instance-validator is Module B. It uses bpg-pyarrow to load the dataset and its metadata, then applies structural, primary key, foreign key, and GQL checks. It reports text or JSON and exposes configurable validation profiles. The separate bpg-layout-validator examines the canonical layout and metadata. Both packages can provide a bpg-validate command, so scripts should pin the intended package and exit code contract.

11.3. Neo4j connector

neo4j-bpg is Module C. It maps BPG node rows to Neo4j nodes and edge rows to relationships, using batches through a driver or procedure. It needs a stable mapping from BPG node IDs to created database nodes before loading edges. The design discusses an external loader and a Neo4j procedure style implementation. Labels become node labels or relationship types according to connector policy; textual value lists and repeated property keys also need an explicit mapping policy. Batch size and optional parallelism are operational settings, not format requirements.

11.4. Additional tools

bpg-graphfaker is the primary producer reference for canonical schema and footer metadata. bpg-container packages and extracts .bpg. bpg-query uses DuckDB for SQL and a limited CypherLite subset. Import, export, diff, RDF interoperability, and APOC projects integrate the same dataset model with other systems. Their APIs evolve separately from this file specification.

12.2. Command examples

The commands below come from the individual tool projects. They assume that each tool has been installed according to its repository instructions. Paths are illustrative; replace them with files in your workspace. The graph producer creates a pair of Parquet files, which subsequent examples inspect, validate, package, query, or convert.

Generate a graph with bpg-graphfaker

# Run after installing the Knows BPG format plugin.
knows -n 20 -e 10 -f bpg sample.parquet
# Outputs: sample_nodes.parquet and sample_edges.parquet

The Knows plugin uses the output base name and adds _nodes.parquet and _edges.parquet. For tools that expect canonical names, place copies of those files at dataset/nodes.parquet and dataset/edges.parquet.

Inspect a dataset with bpg-pyarrow

bpg-info dataset/
bpg-info -v dataset/
bpg-dump-metadata dataset/
bpg-dump-metadata -f yaml dataset/

bpg-info reports dataset information; bpg-dump-metadata shows the GQL manifest and field annotations.

Validate structure and instance data

# bpg-layout-validator: two explicit Parquet paths, JSON result.
bpg-validate --json dataset/nodes.parquet dataset/edges.parquet

# bpg-instance-validator: one dataset directory and a report file.
bpg-validate dataset/ --json-out validation.json -v

These are separate packages that can install the same bpg-validate executable name. Use one package environment at a time, or invoke the instance validator as python -m bpg_instance_validator dataset/ --json-only. Their exit codes differ: the layout validator returns 0 for valid input, 1 for validation errors, and 2 for unreadable files; the instance validator returns 0 for no findings, 1 for warnings only, and 2 or higher for errors.

Package, extract, and compare

bpg-create --nodes dataset/nodes.parquet --edges dataset/edges.parquet \
  --output graph.bpg --validate-profile-schema
bpg-extract graph.bpg --output-dir extracted/
bpg-diff graph.bpg extracted/ --json

The --metadata argument is optional when creating a container. bpg-diff also accepts two directories or two containers and returns exit code 1 when differences are found.

Query Parquet files with bpg-query

bpgq --sql "SELECT id, source_node_id, target_node_id FROM bpg_edges LIMIT 5" \
  --node dataset/nodes.parquet --edge dataset/edges.parquet --format table
bpgq --query "MATCH (n:Person) RETURN n.id LIMIT 5" \
  --node dataset/nodes.parquet --edge dataset/edges.parquet --format json

The bpgq CypherLite implementation supports a limited MATCH, WHERE, RETURN, and LIMIT subset. The SQL form uses DuckDB relations named bpg_nodes and bpg_edges.

Convert GraphML or GraphSON

bpg-import graph.graphml --format graphml-apoc --output-dir graphml-imported/
bpg-import graphson3.ndjson --format graphson-3 --output-dir graphson-imported/ --no-metadata
bpg-export --nodes graphml-imported/nodes.parquet --edges graphml-imported/edges.parquet \
  --format graphson-3 --output graphson3.ndjson

The importer generates sequential INT64 identifiers. With --store-input-ids, it also preserves source IDs in the _import.original_id property.

Import RDF 1.2

rdf12-bpg-interop input.ttl --output-dir rdf-graph/
rdf12-bpg-interop input.nt --output-bpg rdf-graph.bpg \
  --prefix ex=http://example.org/

The RDF tool preserves RDF terms and asserted triples in a graph projection; it can emit a Parquet directory, a container, or both.

Prepare a Neo4j load

# Dry run; requires neo4j-bpg and its bpg-pyarrow dependency.
bpg-neo4j-load dataset/ --dry-run --json-only

# Once configured with a Neo4j connection, run the loader.
bpg-neo4j-load dataset/ --config neo4j-load.yaml

The Neo4j connector maps BPG node IDs to database nodes before creating relationships. Its configuration controls URI, credentials, batch size, and merge behavior. The APOC integration offers a separate procedure interface, for example CALL apoc.import.bpg.graph(nodesFile, edgesFile, config) inside Neo4j.
